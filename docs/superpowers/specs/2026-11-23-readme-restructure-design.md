# README 重构设计（方案 A：精简入口 + docs 拆分）

## 意图与原因

现有 README 共 393 行，事实基本准确，但更像运维手册：第一屏没有回答"这是什么、我该不该用"，章节顺序把故障排查夹在部署和分析之间，近期功能（修改密码、整场 ZIP 下载、删除合集）没有写进去。目标读者是第一次打开仓库的访客，其次是已经跑起来的用户。

## 目标

- 首屏说清：项目是什么、只录音还是能识别、跑在哪、需要什么。
- README 控制在 120–150 行，按"是什么 → 能做什么 → 怎么用 → 深入参考"排列。
- 细节不丢：部署、API、架构、排障、验收拆到 `docs/`，README 只留导航和最短路径。
- 补齐近期功能：修改登录密码、整场音频 ZIP 下载、删除合集、`reset-password` / `init-auth` 子命令、ValuSense 与 `douyin-live-sense` 的关系。
- 加一张真实界面截图（服务运行后截取，放 `docs/images/`）。

## 非目标

- 不改任何代码、接口或行为。
- 不写英文版。
- 不做视觉改版。

## 反目标（这样算失败）

- README 又变成 300 行以上的手册。
- 拆分后原文里的安全边界、平台限制、许可说明丢失。
- 截图与当前界面不一致（例如旧版菜单）。

## 约束

- 所有描述必须与代码一致；以 `src/douyin_live_sense/app.py`、`static/`、`scripts/`、`pyproject.toml` 为准。
- 中文写作，保持现有术语（场次、切片、整场分析、单片复核、识别方式）。
- 不把 `.env`、Token、Cookie、真实房间号写进文档。

## 采用方案

A：README 做入口，`docs/` 承接参考内容。备选 B（单文件重排）会让首屏继续被参考内容淹没；C（运维手册）不适合公开仓库的第一次访问。

## README 结构

1. 标题与一句话定位（ValuSense，包名/命令 `douyin-live-sense`，仅录音优先）。
2. 界面截图。
3. 适合与不适合（一段：中文普通话、单房间、本机运行、16 kHz 存档）。
4. 功能一览（保留现有表格，删到 10 行以内）。
5. 快速开始（3 步：`setup.sh` → `run.sh` → 登录；注明默认仅录音，完整识别需 `--extra analysis` + Token）。
6. 日常使用（守卫输入格式、本机录音、网站配置、整场/单片分析、档案回听/ZIP 下载/删除合集、修改密码）。
7. 数据与磁盘（目录树、115 MB/小时、15 GB 模型、不自动清理）。
8. 配置（只列最常用的 5–6 个环境变量，其余指向 `docs/deploy.md`）。
9. 部署（本机默认 + 反代/隧道/systemd 一段话 + 链接）。
10. 常见问题（403 Host、登录循环、WebSocket、模型 401/403，4 条）。
11. 文档导航（`docs/` 索引）+ 开发与验证命令。
12. 边界、许可。

## docs 拆分

| 文件 | 内容 |
| --- | --- |
| `docs/deploy.md` | 本机、局域网、Caddy、Cloudflare/Tailscale、systemd、平台支持矩阵、完整环境变量表 |
| `docs/analysis.md` | 识别方式、模型清单与下载、分析队列与进度、整场/实时/单片复核、人物编号范围、文本与下载范围 |
| `docs/architecture.md` | 模块职责、数据流、模型替换与适配器、音频切段与时间基准、重启恢复 |
| `docs/api.md` | HTTP API 表、分页与游标、状态码、WebSocket 协议 |
| `docs/troubleshooting.md` | 现有故障排查条目 + 采集/磁盘/模型常见问题 |
| `docs/development.md` | 测试与检查命令、验收工具、CI 说明、VERIFICATION 链接 |
